# Host 168: device-scoped driver maintenance, 2026-10-28

The installed October 9 source already included upstream revision
`17535a0ab1e8d8a9797e096ac5a2495f3da16d2c`, including additional SM/TPC and
DRAM/SRAM ECC patches. The comparison against Forgejo main
`1cd1bbc88ecacd95c5d74c8d1b5d5c33b3bf488c` found an additional inactive-HWE
kernel staging guard; it was retained for this build. The old and rebuilt
`kernel_gsp.c` compared identically: the SM/ECC implementation was not removed.

The current card is reported by the owner as an RTX 4090 modified to 48 GB,
not a CMP170. Actual post-reboot memory size and negotiated PCIe link still

P2P and HBM modes both disabled. The existing matching 615.71.09 userspace was
not replaced. All five staged module versions, vermagic values and deployment

`2359c9bd1e8609a75bd52efedef7537d0711dae03b8aa6705924b86e4c5ed343`;
its expected srcversion is `A5878609C52F76EA15B8E0D`.

Modules and initramfs were installed for the next boot without unloading the
live driver. The previous modules, initramfs, helper and blacklist were saved
under `/var/lib/cmp170-unlock/scope-168-20261028/backup`. The deployment manifest

Pre-maintenance observations included NVIDIA Xid 79 (GPU fallen off bus) and
Xid 154, following an earlier nouveau/GSP failure. These observations alone do

An authorized reboot was scheduled through
`cmp170-scope-reboot-168-20261028`; the prior boot ID was
`e51fcf2f-1c93-4c0f-b8bf-e880aa9afc88`. Following that request, the host was
unreachable over SSH and the panel endpoint during follow-up checks.
The host subsequently returned with boot ID
`2b629975-5221-4f4b-ac8f-0637776eaba6` (boot at approximately 16:19 UTC).

**CUDA memory-size verification, PCIe-under-load checks and Qwen inference tests
remain blocked by GPU initialization failure.**

## Subsequent boot and CUDA check

At 16:31 UTC the host returned with another boot ID,
`47d1e3eb-3669-4583-884a-5b8467d8796e`. The expected scoped module was loaded.
NVIDIA-SMI reported RTX 4090, 49140 MiB, 615.71.09, idle Gen1 x16 and maximum
Gen4 x16. No Xid or adapter-initialization failures were found in this boot.
This successful startup does not by itself explain the previous boot failure.

A bounded 20-second test inside `ai-manager` repeatedly copied a 256 MiB pinned
host buffer to CUDA and multiplied 2048-square FP16 matrices. All five link
samples were Gen4 x16; the test completed 1948 cycles in 20.1 seconds, with
finite matrix output and a verified transferred value. Reported temperature
remained 33–40 C and sampled power stayed below 115 W. This is a small CUDA/
PCIe smoke test, not a full 48 GB VRAM qualification or sustained stability test.

The existing `cyankiwi/Qwen3.8-27B-AWQ-INT4` was subsequently started through
the panel on standard vLLM 0.32.0, GPU 0 / TP1, BF16, FlashAttention 2, prefix
caching, 32768 context, max one sequence and 0.90 memory utilization, without
speculative decoding. The previous launch configuration was saved privately
before the revision-checked update. The engine reached running/health 200.

Four sequential streamed requests completed: arithmetic returned 323 for
17*19, Russian text was coherent, JavaScript contained no Markdown and its three
assertions passed, and a repeated Russian prompt returned the same answer.
The three substantive outputs decoded at approximately 50.8 tokens/s. TTFT was
77–108 ms for the first three requests and 2627 ms for the repeated prompt;
these tiny tests do not establish prefix-cache or long-context performance.
Afterward the card was still Gen4 x16, 42286 MiB allocated, 48 C; PCIe error
status was clear, and no Xid/adapter failures appeared in the current boot.
The model was left running for the owner. Longer stability/VRAM testing and the
cause of the earlier failed boot remain unverified.

## Later TRELLIS failure: stability is not established

Following another reboot, boot ID `1c50ec72-e679-4e8d-bbb5-f26ec780abaf`,
the official TRELLIS.2 runtime started at 17:10:21 UTC on 2026-10-28. At
17:15:02 the kernel reported Xid 175, `GPU memory subsystem timeout (type 1)`,
for its Python PID 2981, together with a failed TLB invalidation and GSP timeout.
At 17:15:04 Xid 154 changed recovery action to PF FLR. NVIDIA-SMI subsequently
reported `GPU requires reset`; the Python process was later defunct.

The application traceback occurred during GLB attribute sampling, inside the
FlexGEMM Triton grid-sampling autotuner: CUDA event timing failed with
`Both events must be completed before calculating elapsed time`. The installed
Triton benchmark already synchronizes before reading event times, so adding a
missing synchronization is not an established fix. The timing failure may be
secondary to the GPU fault. The runtime's HTTP health handler returns readiness
without testing device health; its HTTP 200 responses do not establish CUDA
health. Endpoint PCIe status at inspection was Gen4 x16, with no reported
correctable or uncorrectable PCIe status errors.

These findings do not distinguish a kernel/driver fault from hardware or
modified-memory instability. A full VRAM check and controlled comparison with
an unmodified matching driver and an alternative postprocessing path are still
needed after device recovery. No additional workload, reset or reboot was
performed during this read-only failure inspection. Earlier startup and short
inference successes must not be interpreted as sustained stability validation.

Offline checks: 63 unit tests passed, one skipped. The new device-scope C tests
ran successfully, and the actual NVIDIA module build completed. ECC status
reporting is not independent evidence of effective hardware ECC protection.
